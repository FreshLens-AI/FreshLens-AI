# 3.1 Functionality — Vendor (Mobile)

This section specifies the functional requirements of the FreshLens mobile application,
used by the **Vendor / Shop Owner** role. The mobile app is built with **React Native
on Expo (SDK 57)** and is the vendor's only interface into the platform: it is used to
capture shelf images, confirm stock quantities, submit scans, and monitor inventory and
freshness status. No use-case diagrams are included per template instructions; each
function below is described in natural language with its inputs, processing, and outputs.

All vendor-facing data is scoped to the authenticated vendor's tenant. No mobile
function in this section requires an on-device CNN: freshness classification always runs
asynchronously on the backend, consistent with the platform's async-scan architecture
(Proposal §2, §5.2; Feasibility Study §2.2).

---

## FR-3.1.1 Authentication / Login

**Description**
Vendors authenticate into the mobile app using tenant-aware credentials managed by
Supabase Auth. A successful login establishes the vendor's session and tenant context,
which the app attaches to every subsequent request so that PostgreSQL Row-Level
Security can scope all reads and writes to that vendor's data.

**Inputs**
- Vendor email/username and password (or other Supabase-supported credential method).
- Device/session metadata (used for session persistence, not for identification).

**Processing**
- The app submits credentials to Supabase Auth over HTTPS.
- Supabase validates credentials and returns a session token (JWT) encoding the
  vendor's identity and tenant ID.
- The app stores the session token securely on-device and attaches it as a bearer
  token to all subsequent API calls.
- On invalid credentials, the app displays an inline error and does not establish a
  session.
- On session expiry, the app prompts re-authentication before allowing further
  scanning or dashboard access.

**Outputs**
- An authenticated session scoped to exactly one vendor tenant.
- Navigation to the vendor home/dashboard screen on success.
- A visible, non-technical error message on failure (e.g. "Incorrect email or
  password"), with no indication of which field was wrong, to avoid leaking account
  existence.

**Notes**
- No cross-tenant data is ever fetched at this stage or later; tenant isolation is
  enforced at the database layer (Row-Level Security), not only by the mobile app
  hiding UI elements.

## FR-3.1.2 Camera Capture

**Description**
The vendor captures a photo of a single product type using the device camera,
initiating a scan. Version 1 supports exactly one product per photograph (Proposal
§5.2); multi-item shelf detection is explicitly out of scope for this release
(Proposal §5.3).

**Inputs**
- Live camera feed from the device, accessed via Expo's camera module.
- Vendor's shutter action (tap to capture).
- Optional retake action if the vendor is not satisfied with the captured image.

**Processing**
- The app requests and confirms camera permission on first use.
- On capture, the app stores the image locally as a temporary file and displays a
  preview screen (accept / retake).
- The app performs only lightweight client-side checks (e.g. confirming a non-empty
  image file was produced) — no image classification or quality scoring happens
  on-device.
- On accept, the captured image is passed forward to the quantity-confirmation step
  before upload.

**Outputs**
- A single locally-held product image ready for quantity confirmation and submission.
- A preview UI state allowing the vendor to retake before proceeding.

**Notes**
- No on-device CNN or inference is required at capture time; this preserves the
  architecture rule that the FreshLens Two-Tier Classifier runs only on the backend,
  asynchronously (Feasibility Study §2.2, item 4).

## FR-3.1.3 Quantity Confirmation

**Description**
Immediately after capturing (or accepting) a photo, the vendor manually enters or
confirms the quantity of the product being scanned. Version 1 relies entirely on
vendor-entered quantities; automatic count verification from the image is not part of
this release (Proposal §5.2, §7.5).

**Inputs**
- Vendor-entered numeric quantity (integer, vendor's chosen unit — e.g. count, kg,
  as configured for that product category).
- The captured product image from FR-3.1.2, shown alongside the quantity field for
  context.

**Processing**
- The app presents a numeric input (with sensible default/last-used value where
  applicable) next to the captured image.
- The app validates that the entered quantity is a positive number before allowing
  the vendor to proceed.
- The confirmed quantity is attached to the pending scan payload, along with the
  image and the vendor's tenant context.

**Outputs**
- A validated (image, quantity) pair ready for submission.
- An inline validation error if the quantity is missing, zero, or non-numeric,
  blocking submission until corrected.

**Notes**
- This is disclosed to vendors as an explicit operating assumption of Version 1:
  recorded quantities are only as accurate as vendor entry, since no automated count
  verification exists yet (Feasibility Study §2.4).

## FR-3.1.4 Submit Scan and View Result Status

**Description**
The vendor submits the confirmed (image, quantity) pair as a scan. The app uploads
the image and creates a scan record, then lets the vendor track that scan's status
(queued → processing → completed) without blocking on classifier processing time,
consistent with the platform's asynchronous inference pipeline (Proposal §2;
Feasibility Study §2.2, item 5).

**Inputs**
- The validated (image, quantity) pair from FR-3.1.2 and FR-3.1.3.
- Vendor's tenant/session context from FR-3.1.1.

**Processing**
- The app uploads the image to Cloudflare R2 object storage and calls the FastAPI
  backend to create a scan record referencing the stored image, the confirmed
  quantity, and the vendor's tenant ID.
- The backend enqueues a background job (Redis + Celery) for the FreshLens Two-Tier
  Classifier and returns an immediate API response (scan accepted, status:
  "queued") — the API does not wait for classification to complete.
- The mobile app marks the scan as "Processing" in the vendor's scan list/dashboard.
- A Celery worker later runs the two-tier classification (produce identification,
  then Fresh/Medium/Spoiled freshness scoring) and writes the result back to the
  database.
- The app polls or refreshes scan status so the vendor can see progression from
  "Processing" to "Completed" without needing to keep the screen open or resubmit.
- If classification fails (e.g. unreadable image), the scan status is set to
  "Failed" with a vendor-facing reason, and the vendor can retake and resubmit.

**Outputs**
- A scan record visible in the vendor's dashboard, showing: product image
  thumbnail, confirmed quantity, timestamp, and current status
  (Queued / Processing / Completed / Failed).
- Once completed: the identified produce type, freshness classification
  (Fresh / Medium / Spoiled), and a confidence score, displayed to the vendor.

**Notes**
- Because inference is decoupled from the request/response cycle, the app remains
  responsive immediately after submission regardless of how long classification
  takes — this is a hard architectural constraint, not a UX nicety (Feasibility
  Study §2.2, "Performance" in §3 Considerations).

## FR-3.1.5 View Alerts / Batch Context

**Description**
The vendor views alerts relevant to their own inventory directly on mobile: low-stock
alerts and static aging alerts, along with the batch context (intake date, quantity
received, quantity remaining, category shelf-life) that explains why an alert was
raised.

**Inputs**
- Vendor's tenant context (to scope which alerts/batches are visible).
- Backend-computed alert data: low-stock threshold comparisons and shelf-life-based
  aging comparisons.

**Processing**
- Low-stock alerts: the backend compares each product's current recorded quantity
  (from batch data) against the vendor-configured threshold for that product; if the
  quantity falls below the threshold, a low-stock alert is generated and made
  available to the mobile app.
- Aging alerts: the backend compares each batch's time-since-intake against the
  administrator-configured typical shelf-life for that product's category; if the
  elapsed time exceeds the shelf-life while a large proportion of the received
  quantity remains unsold, an aging alert is generated. This is a static lookup-table
  comparison in Version 1, not a learned prediction (Proposal §5.2, §5.3).
- The mobile app fetches the vendor's current alerts and renders them as a list,
  each linked to the underlying batch (intake date, quantity received, quantity
  remaining, category shelf-life) so the vendor has enough context to act (e.g.
  discount or remove aging stock, reorder low-stock items).
- Alerts are read-only on mobile in Version 1: the vendor views and acts on them
  in their own stock-handling process; no in-app alert-dismissal workflow is
  specified beyond viewing.

**Outputs**
- A list of active alerts (low-stock, aging) scoped to the vendor's own tenant.
- Batch context displayed per alert: intake date, quantity received, quantity
  remaining, and the category's configured shelf-life.

**Notes**
- The underlying batch data model already carries the fields needed for future,
  learned "nearing spoilage" alerts (Version 2), so no schema change is needed
  when that feature is added later (Proposal §5.2, §5.3).
